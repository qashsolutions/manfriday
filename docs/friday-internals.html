Friday Internals

The contracts that clear the design gate for Man Friday: the Convex data model, the template spec that turns a trend into a render plan, the publish-layer contract that keeps TikTok and YouTube behind one interface, and the learning loop that makes the feed laser-focused. Everything here follows the locked decisions D1–D5 and the determinism-first principle.

Contract 1 of 3

Convex schema

Design choices worth naming before the code: publications are normalized away from posts (one post → N platform publications, each with its own status, retries, and metrics — this is what makes the publish layer platform-agnostic); the render queue lives in the database (the Python worker long-polls renderJobs, so job state survives worker restarts and is observable from the app); credits are an append-only ledger, never a mutated counter; and YouTube's daily quota gets its own counter table so the budgeter is transactional.

// convex/schema.ts

import { v } from "convex/values";

export default defineSchema({

    userId: v.id("users"),

    name: v.string(),
    oneLiner: v.string(),

    tone: v.array(v.string()),

    screenshotIds: v.array(v.id("_storage")),     // scraped product shots for slides

    .index("by_active_score", ["active", "engagementScore"]),

  concepts: defineTable({                         // one generated candidate
    userId: v.id("users"),
    brandId: v.id("brands"),
    templateId: v.id("trendTemplates"),
    briefVersion: v.number(),
    status: v.union(v.literal("draft"), v.literal("preview_ready"),
                    v.literal("kept"), v.literal("skipped"),
                    v.literal("render_queued"), v.literal("rendered"),
                    v.literal("failed")),
    slots: v.any(),                               // call site 2 output, schema-validated

    videoId: v.optional(v.id("_storage")),

    conceptId: v.id("concepts"),

    status: v.union(v.literal("pending"), v.literal("claimed"),
                    v.literal("running"), v.literal("done"), v.literal("failed")),

    error: v.optional(v.string()),
  }).index("by_status_priority", ["status", "priority"]),

  socialAccounts: defineTable({
    userId: v.id("users"),
    platform: v.union(v.literal("tiktok"), v.literal("youtube")),
    handle: v.string(),
    accessToken: v.string(),                      // encrypted; touched only in actions
    refreshToken: v.string(),
    expiresAt: v.number(),
    status: v.union(v.literal("connected"), v.literal("expired"),
                    v.literal("revoked")),
  }).index("by_user", ["userId"]),

  posts: defineTable({                            // one scheduling decision
    userId: v.id("users"),
    conceptId: v.id("concepts"),
    publishAt: v.number(),
    captionByPlatform: v.any(),                   // adapter-built per-platform text
  }).index("by_user", ["userId"]),

  publications: defineTable({                     // one post × one platform
    postId: v.id("posts"),
    accountId: v.id("socialAccounts"),
    platform: v.union(v.literal("tiktok"), v.literal("youtube")),
    status: v.union(v.literal("queued"), v.literal("publishing"),
                    v.literal("live"), v.literal("draft_fallback"),
                    v.literal("failed")),
    platformPostId: v.optional(v.string()),
    publishAt: v.number(),
    attempts: v.number(),

  metrics: defineTable({                          // time-series snapshots per publication

    capturedAt: v.number(),
    views: v.number(), likes: v.number(),
    comments: v.number(), shares: v.number(),

    userId: v.id("users"),
    delta: v.number(),                            // negative on spend
    reason: v.string(),                           // "final_render" | "avatar_render" |
                                                  // "monthly_grant" | "call_bonus" | ...
    refId: v.optional(v.string()),
  }).index("by_user", ["userId"]),

  quotaCounters: defineTable({                    // e.g. YouTube uploads/day, global
    key: v.string(),                              // "youtube:2026-09-04"
    used: v.number(),
    limit: v.number(),
  }).index("by_key", ["key"]),

Contract 2 of 3

Template spec — trend format → render plan

The template is where determinism-first lives or dies. A template encodes everything structural — slide count, timing, layout positions, style tokens, music mood, platform constraints — as authored data. Claude sees only the slots array and returns text for each slot; the worker then merges slot values into the renderPlan and renders without any model in the loop.

Spec fields (templateSpec v1.1)

FieldTypeRule
specVersionnumberWorker refuses versions it doesn't know
formatenumslideshow · hook_video · avatar
platformsenum[]["tiktok"] for slideshows; ["tiktok","youtube"] for video formats — the schedule UI reads this, never hardcodes it
slots[]typed listEach: id, type (text | script), maxChars or targetSeconds, guidance — the per-slot creative direction that goes into the Claude prompt — and use (render default · publish): publish slots (caption) are consumed by the publish layer, never by the renderPlan
renderPlanobjectFormat-specific composition tree; every slotRef must name a declared slot; backgrounds are brand_screenshot · gradient · stock(query) — never generative
styleTokensrefsResolved by the worker from the brand's palette — templates stay brand-neutral

Validation — authoring time and generation time

  • Template lint (authoring): every slotRef resolves to a declared slot; every render slot is referenced and no publish slot is; slideshow slide count 4–8; video plans total ≤ 60s (fixed holds + script targetSeconds); platforms consistent with format (a slideshow declaring youtube is a lint error).
  • Slot-fill validation (generation): call site 2 uses structured outputs with a JSON schema generated from slots[] — maxChars enforced, one retry on violation, then the concept is dropped from the batch (never padded or truncated silently).
  • Compatibility: concepts pin briefVersion and specVersion; editing the brief doesn't mutate existing concepts, and the worker refuses a plan whose spec version it doesn't implement.
  • Light-editor mapping: the editor's three powers are exactly slot rewrites (hook, per-slide lines), voice choice, and background swaps — the editor edits the concept's slot values and render plan overrides, never free-form video. The UI constraint and the data model are the same shape on purpose.

v1.1 amendments — from hand-validation, 4 Sep 2026

The spec was validated by hand-producing three real posts (one per format) with zero LLM calls — templates, lint, deterministic renderer, and findings live in validation/template-spec/ in the repo. Three gaps found and fixed:

  • Publish slots (F1): v1's lint failed its own worked example — caption is consumed by the publish layer, so "all slots referenced" was wrong as written. Fixed via use: render | publish above.
  • Video render plans (F2, F3): canonical shapes now authored. hook_video: shots[] each with holdSeconds or flex: true — exactly one flex shot absorbs the VO duration, so templates never author a timeline; plus voice {slotRef, tts}, captions {from, styleToken, position}, durationCapSeconds. avatar: character {pick}, speech {slotRef, tts, lipsync: lazy_on_right_swipe}, captions, overlay {slotRef, showSeconds}, endCard {holdSeconds, bg, text}. Timing re-checks at generation time against actual TTS duration vs durationCapSeconds: tempo nudge ≤ 1.08×, else drop the concept — never silently truncate the script.
  • Stock fallback (F4): stock(query) falls back to gradient(brand-dark-2) at render time; picking the stock provider is a pre-M1 open item and renders never block on it.

Contract 3 of 3

Publish-layer contract

One interface, two adapters, zero platform knowledge outside them. The scheduler and UI speak only in publications; everything TikTok- or YouTube-specific lives behind PublishAdapter. This is what makes Instagram a fast follow instead of a refactor.

// convex/publish/adapter.ts — implemented by tiktok.ts and youtube.ts (Convex actions)
export interface PublishAdapter {
  platform: "tiktok" | "youtube";

  /** Format gate — the schedule UI calls this, never hardcodes rules. */
  supports(format: "slideshow" | "hook_video" | "avatar"): boolean;

  /** Pre-flight: caption length, media specs, account health. Cheap, no side effects. */
  validate(input: PublishInput): ValidationResult;

  /** Idempotent: keyed on input.idempotencyKey. Safe to call again after a crash. */
  publish(input: PublishInput): Promise<
    | { kind: "live"; platformPostId: string }
    | { kind: "draft_fallback"; platformPostId: string; userAction: string }
    | { kind: "retryable"; error: PublishError }
    | { kind: "fatal"; error: PublishError }>;

  /** Poll a publication that platform-side processes async. */
  fetchStatus(platformPostId: string): Promise<"processing" | "live" | "rejected">;

  /** One metrics snapshot; the polling cadence is the caller's job. */
  fetchMetrics(platformPostId: string): Promise;

  /** Refresh OAuth; returns "expired" when the user must reconnect. */
  refreshAuth(account: SocialAccount): Promise<"ok" | "expired">;
}

export type PublishError = {
  code: "AUTH_EXPIRED" | "QUOTA_EXCEEDED" | "MEDIA_REJECTED"
      | "POLICY_BLOCKED" | "TRANSIENT";
  message: string;
};

Cross-cutting rules

  • Scheduler: a Convex scheduled function runs every minute, scans publications.by_due, and invokes the adapter as an action. At most one in-flight publish per account (per-account mutex via claim pattern) so platform rate limits are respected by construction.
  • Idempotency: idempotencyKey = publication._id travels into each platform request where supported; adapters must tolerate a retry discovering the post already exists (fetch-before-create on retry paths).
  • Metrics cadence: snapshots at +1h, +6h, +24h, +72h, +7d, then daily through day 30 — a scheduled function fans out over live publications; each snapshot is one row in metrics, and the "more like this" ranker reads snapshots, never live APIs.
  • Timezones: publishAt is stored UTC; slot suggestions are computed in users.timezone and converted at write time.
  • Token hygiene: OAuth tokens are only ever decrypted inside Convex actions (the adapter layer); they never reach the browser, the worker, or logs.
  • Instagram later: a third adapter implements the same interface; the only app change is an entry in the platform enum and the connect UI — the state machine, scheduler, and metrics pipeline are untouched.

Design-gate status: with these three contracts plus the 8-artboard canvas and clickable prototype, the remaining gate items are the two API applications (TikTok audit, YouTube quota increase — paperwork, start immediately) and validating the template spec by hand-producing 3 real posts with it. Then the gate clears and M1 begins.

Contract 4 of 4 · added 4 Sep

The learning loop — how Friday gets laser-focused

North star, in the founder's words: options so laser-focused the user swipes right, uploads, and makes more money. Two numbers measure it — right-swipe rate (target: ≥30% by week 4 of use; see 10, keep 3+) and tracked clicks to the user's product per week. Five feedback signals, in ascending strength, feed both:

SignalWhat it teachesStored inHow it's used
1 · Brief editsGround truth about product, audience, tone — corrections we could never scrapebrands (+ briefVersion)Every slot-fill call is grounded in the corrected brief
2 · SwipesPer-user preference on template × hookPattern × formatconcepts.status + swipedAtPlain-stats per-user template scores; feed mix is 80% exploit / 20% explore — deterministic, no ML infra
3 · Editor editsThe user's actual voice: Friday's draft → user's rewrite pairsvoiceEdits (new)Last N pairs ride into call site 2 as few-shot examples — Friday writes more like the user with every correction
4 · Post metricsWhich format attributes actually perform (views, watch %)metricsAttribute-level ranking powers "more like this" and updates niche-wide engagementScore priors — new users cold-start from what already wins in their niche
5 · Link clicksThe money signal: which posts send people to the producttrackedLinks + linkClicks (new)Top of the reward ladder; the ranker optimizes clicks over raw views. True revenue attribution is v2; beta customer calls cover the last hop

The reward ladder the ranker walks, weakest to strongest: right-swipe → published → views → watch % → click to product. A template that gets kept but never clicked decays; a modest-view format that drives clicks rises. Everything is plain arithmetic over the tables above — consistent with determinism-first, auditable, and replayable.
